# RC4 — редактура прохода и проверка результата

## Запрос

Убрать лишние кнопки и строки. После комиссии сразу показать готовое изображение 9:16: имя, аватар, результат и настоящий кадр взрыва из части C. Экран, сохраняемый PNG и файл для отправки должны быть одной и той же карточкой.

## Найденные повторы в RC3

- Главная: две кнопки запуска, два списка A/B/C, проходной балл в нескольких местах, повтор кампании/года/предмета, внешний переход к официальной GTA VI в основном пути.
- Вопросы: номер и тип задания повторяются в нескольких полосах; ещё раз указаны предмет и вариант; кнопка «На главную» дублирует верхнюю; общая инструкция о выборе ответа повторяется на каждом простом вопросе.
- Вступления: маршрут, буква, название, звёзды, три статистики и две инструкции одновременно.
- Промежуточный итог: лишний маршрут, повтор порога/дисклеймера, отдельное «Сохранить и выйти» при наличии общей навигации и автоматического сохранения.
- Результат: отдельный сертификат и отдельная карточка истории, множество кнопок, подробный разбор и технические показатели сразу на экране.

## Принцип сокращения

Один главный CTA. У результата — готовая картинка, одно основное действие отправки/сохранения по возможностям устройства, подробности под раскрытием. На вопросе остаются часть и номер, вопрос/медиа, варианты, основное действие. Обязательная атрибуция фото сохраняется. Звук, пауза, повтор после сбоя и доступное объяснение ошибки остаются.

A сохраняет немедленную правильность и промежуточный итог. B показывает промежуточный балл после части, а ключ — в финальном разборе. C до окончания B остаётся сюрпризом. Система баллов и вопросы в этой итерации не меняются.

## Важные границы интеграции

- Захваченный кадр нужно принять до releaseNative при переходе к результату.
- Кэш карточки должен учитывать попытку, кадр и аватар, а не только номер варианта и баллы.
- Результат готовится до клика «Поделиться». navigator.share с готовым File вызывается непосредственно из пользовательского действия, чтобы не потерять активацию iOS.
- При отсутствии публичного HTTPS upload endpoint нельзя обещать прямое открытие Telegram shareToStory. Сохранение изображения/системная отправка остаются доступными.
- Ни появление карточки, ни окончание комиссии не публикуют изображение автоматически.
- Если C не запускалась или реальный кадр недоступен, нельзя выдавать посторонний взрыв за момент игрока. Карточка без кадра остаётся честным результатом.

## Проверка

Выполнена независимая проверка `dist/app.js` и жизненного цикла карточки. Команда:

```sh
node --test tests/rc4-result-flow.test.cjs
```

Результат: **9 тестов, 9 пройдено, 0 ошибок**.

1. Готовая PNG появляется прямо на экране результата; отдельного сертификата и дополнительного окна для получения картинки нет. Разбор свёрнут. Само появление результата ничего не публикует, не загружает на сервер и не скачивает.
2. Сохранение использует тот же Blob, который показан на экране. Web Share получает File с теми же байтами непосредственно в обработчике пользовательского клика.
3. Баллы 0, 59, 60 и 100 правильно попадают в изображение; сумма частей сохраняется, проходной порог — 60.
4. Кадр финальной сцены читается до уничтожения нативного движка, сохраняется в попытке и передаётся в генератор карточки. Захват не начисляет баллы повторно.
5. Ошибка декодирования кадра не ломает результат: карточка получает `highlightImage: null`, баллы остаются доступны.
6. Ошибка экспорта PNG показывает действие повтора; неготовое изображение нельзя отправить. Повтор успешно восстанавливает результат.
7. Позднее завершение старого экспорта не подменяет новую попытку и не создаёт для неё старый object URL.
8. Поздняя загрузка аватара меняет ключ карточки. Если повторно открыть результат, пока новая PNG ещё кодируется, оба вызова ждут новую генерацию; готовый старый кэш не возвращается под новым ключом. После обновления в отправку попадают новые байты с аватаром.
9. При настроенном Telegram upload endpoint загрузка начинается только после явного клика. На сервер уходит ровно показанная PNG, без Telegram initData и с `credentials: omit`; редактор сториз получает проверенный HTTPS URL.

Также прочитан нативный путь `highlight-capture.js` → `native.js` → `vice-port.js`: захват выполняется после отрисовки до события завершения, а сообщение проверяется по origin/source/session. Лучший кадр сохраняется между сценами; очистка прекращает захват и освобождает промежуточные поверхности. Лимит 15 проб покрывает текущую последовательность одной взрываемой цели, поездки и трёх финальных целей, включая резервные кадры.

## Конфигурация и границы проверки

В поставляемом `config.js` публичный upload endpoint для Telegram Stories не задан. Поэтому прямое действие «В сториз Telegram» скрыто. Доступны системная отправка файла, если её поддерживает устройство, и сохранение готовой картинки. Экспорт не зависит от стороннего upload сервиса.

Интеграционные тесты исполняют настоящий `app.js`, контент и подсчёт баллов с адаптерами DOM, нативной сцены и PNG-кодировщика. Они проверяют порядок событий, владение попыткой, поведение при сбоях и тождество байтов видимой/отправляемой картинки. Они **не заменяют** визуальную проверку реального WebGL-кадра, браузерного PNG и системного редактора Telegram на телефоне. Качество выбранного взрыва и фактическая публикация сториз этими тестами не утверждаются.
